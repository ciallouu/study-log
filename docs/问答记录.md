## 2026-11-26｜GET 和 POST 是两种"请求方法"，不是两种"输入方式"

### 一句话
**它们都是"客户端对服务器说话"的方式，区别在于"说话的意图"，不在"怎么输入"。**

### 对照表

| | GET | POST |
|---|---|---|
| 意图 | **取**数据（"给我看看"） | **提交**数据（"帮我处理/创建"） |
| 参数放哪 | URL 里：`/api/users?role=1` | 请求 body 里：`{"username":"yuan"}` |
| 会不会改服务器数据 | 不应该改（只读语义） | 通常会改（新增/修改） |
| 能不能重复发 | 可以，发 100 次结果一样（**幂等**） | 不能，发两次可能创建两条（**非幂等**） |
| 浏览器地址栏能直接发吗 | 能（回车就是 GET） | 不能（要用表单或代码） |
| 缓存 | 可被浏览器/CDN 缓存 | 默认不缓存 |
| 长度限制 | 受 URL 长度限制（约 2KB~8KB） | 基本无限制（适合传文件、长文本） |
| 典型例子 | 打开网页、查列表、看详情 | 登录、注册、上传、下单 |

### 为什么 405 和 GET/POST 有关
路由表是按 **"方法 + 路径"** 一起匹配的：

```
POST  /api/auth/login   →  AuthController.login()
```

用浏览器直接打开 `http://localhost:8080/api/auth/login`，浏览器发的是 **GET**，所以：
- 路径 `/api/auth/login` **存在** → 不是 404（404 是"没这条路"）
- 但 **GET + 这个路径** 没有登记 → **405 Method Not Allowed**（"路对，走法不对"）

### 面试口径
> GET 是幂等的查询语义，参数在 URL，可缓存；POST 是非幂等的提交语义，数据在 body，不可缓存。所以登录接口必须是 POST —— 密码不能出现在 URL 里（会进浏览器历史、服务器访问日志、Referer 头）。

## 2026-11-26｜Bean 是什么

**Bean = 由 Spring 容器创建、并交给容器管理的对象。** 不是语法特性，是"归属关系"：

- 你 `new` 出来的 → 普通对象，生命周期你自己管
- 加了 `@Component`/`@Service`/`@Repository`/`@RestController`/`@Configuration` → 被容器接管 → 成为 Bean

### 容器启动干四件事

| 阶段 | 干什么 | 你能观察到的证据 |
|---|---|---|
| ① 扫描 | 扫注解，把类登记进"菜单" | 日志 `Root WebApplicationContext: initialization completed` |
| ② 创建 | 用反射调构造器；**有依赖就先造依赖** | 你的两行打印 —— `UserDao` 先于 `AuthService`，因为 AuthService 依赖它 |
| ③ 存放 | 存进容器（本质是 `Map<beanName, Object>`） | 全项目**只有一份** → 单例 |
| ④ 注入 | 谁在构造器里声明参数，就从容器里取现成的塞进去 | 你从没写过 `new AuthService()` |

### 单例带来的硬约束（明天写拦截器会撞上）
Bean 是单例 → **不能在里面存"当前请求的用户"这类状态**。多个请求共用同一个对象，会串号。
需要请求级数据时：从方法参数里的 `HttpServletRequest` 取，或用 `ThreadLocal`。

## 2026-11-26｜怎么亲眼看到"路由表"

Spring 默认不打这张表。加一行配置就能打印：

```properties
# application.properties
logging.level.org.springframework.web.servlet.mvc.method.annotation.RequestMappingHandlerMapping=TRACE
```

重启后日志里搜 `Mapped`，就能看到类似：

```
Mapped "{[/api/auth/login],methods=[POST]}" onto public ...LoginResponse ...AuthController.login(LoginRequest)
Mapped "{[/api/users],methods=[GET]}"     onto public java.util.List ...UserController.list()
```

这就是 DispatcherServlet 用的那张表 —— **启动时抄好，请求来了查表**。
（看完记得把这行删掉，TRACE 日志很吵）

## 2026-11-28 早上：AI 必须主动抽问源的三条

> 由源在 2026-11-27 15:0x 亲口要求：「这一点明天记得再问我一次」。
> 规矩：**先让他不看笔记口头回答，再对照下面的标准答案打分**，不要先给答案。

### ①（点名要问的）JWT 是 self-contained（自包含）

**问他**：服务端没有存过任何一张 token，它凭什么知道这张票是 test01 的、而不是别人？

**标准答案要点**：
- 身份**写在 token 的 payload 里**（`sub`/`username`/`role`），`parse()` 把 payload 的 Base64URL 解出来，还一个 `Claims`（本质是 Map），`claims.get("username")` 就读到了
- **密钥只负责"没被改过"**，不负责"认人"；解码 payload 根本不需要密钥（谁都能解）
- 一句话：**票里自带全部信息 + 一个防伪标签，所以服务端什么都不用记**

**常见错误答案**（源 11-27 答过一次，要看他有没有改掉）：
- ❌「两次计算结果一样就知道是同一个人」——服务端没有旧票可比

### ② `exp` 为什么不用查库

**问他**：一张 2 小时前签发、现在过期的票，服务端怎么知道它过期了？

**要点**：`exp` 就在 payload 里，`parse` 拿它跟当前时间比，过了抛 `ExpiredJwtException`；因为 `exp` 被签名保护，改了签名就废，所以这个时间可信。

### ③ 两条 401 message 分别属于哪一关

**问他**：`"未登录或凭证缺失"` 和 `"凭证无效或已过期"` 分别在哪一行产生？

**要点**：前者 = 格式关（`JwtInterceptor` 里 `header == null || !header.startsWith("Bearer ")`）；后者 = 验签关（`catch (JwtException | IllegalArgumentException e)`）。排查时先看 message 就知道是哪一关拦的。

### 附：一次 AI 自身的错误记录（2026-11-27）

我（AI）曾说「`Authorization: Bearer ` 只有前缀 → `substring(7)` 得空串 → 走 `IllegalArgumentException` 分支」。
**实测是错的**：用裸 TCP socket 发带尾随空格的报文，Tomcat 按 HTTP 规范裁掉头值首尾空格（OWS），header 变成 `"Bearer"`，在**格式关**就被拦了，消息是「未登录或凭证缺失」。
结论：本项目里 `token` 不可能是空串，`IllegalArgumentException` 分支**实际打不到**，`catch` 它是防御性的。
教训：**只看状态码 401 不能判断是哪一关拦的，必须看 message。**「新知识表述不能靠推理，要实测」这条规矩对 AI 同样适用。

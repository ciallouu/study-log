## 实验零：线程状态机（ThreadStateDemo / StateCompare）

`Thread.State` 只回答一个问题：**这个线程现在在等什么？**

| 状态 | 进入条件 | 唤醒方式 | 有期限吗 |
|---|---|---|---|
| `NEW` | `new Thread()` 之后、`start()` 之前 | 调用 `start()` | — |
| `RUNNABLE` | 就绪队列中，或正在 CPU 上跑 | CPU 调度 | — |
| `BLOCKED` | 等 `synchronized` 锁 | 对方释放锁 | 无 |
| `WAITING` | `wait()` / `join()` / `park()` | `notify()` / `interrupt()` / 目标线程结束 | **无期限** |
| `TIMED_WAITING` | `sleep(n)` / `wait(n)` / `join(n)` / `parkNanos()` | 时间到或 `interrupt()` | **有期限** |
| `TERMINATED` | `run()` 执行完毕 | 不可逆 | — |

实测输出（先猜后跑，猜错第 2 行）：`NEW` → `RUNNABLE` → `TIMED_WAITING` → `TERMINATED`。

三个易混点（实测验证过）：

1. **`RUNNABLE` 包含「就绪」和「运行中」两种物理状态**——Java 不区分「在排队」和「在跑」。
2. **`BLOCKED` 专指等 `synchronized` 锁**，不是泛指「卡住」。等 IO、等 `wait()` 都不是 `BLOCKED`。
3. **`TIMED_WAITING` ≠ 超时**。它是「有期限的等待」（timed = 带时限），不是「超时出错」。`sleep(1)` 和 `sleep(5000)` 状态完全一样。

`join(毫秒)` 的语义是**最多等这么久**，不是必须等满：

| 情况 | `join(3000)` 行为 |
|---|---|
| 线程 1 毫秒结束 | 立刻返回 |
| 线程跑 2.9 秒 | 约 2.9 秒返回 |
| 线程永不结束 | 3 秒时放弃返回，此时 `isAlive()` 为 `true` |

`isAlive()` = 「已 `start()` 且未终止」，与 `getState()` 分工：**`getState()` 看卡在哪，`isAlive()` 看还活着没。**

## 实验一：可见性（VisibilityDemo）

```java
static boolean flag = false;   // 故意不加 volatile
// worker: while (!flag) { i++; }
// main:  sleep(1000) → flag = true → worker.join(3000) → isAlive() ?
```

实测结果：

| 版本 | 输出 |
|---|---|
| `static boolean flag` | `>>> 3 秒还没退出：worker 看不到 flag 的新值` |
| `static volatile boolean flag` | `worker 退出，循环了 2889913059 次`（1 秒内约 28.9 亿次） |

结论：

- 主线程的 `flag = true` **写成功了**，问题在 worker 从不回主内存读。JIT 把 `flag` 读进寄存器后只比较寄存器里的旧值。
- 2889913059 这个数字证明 worker 一直在高速自旋（不是卡死），只是拿不到新值。
- x86 上 `volatile` 读几乎零成本（只有写需要内存屏障），所以能跑到 28.9 亿次/秒——**别怕用 `volatile`**。

## 实验二：原子性（AtomicityDemo）

10 个线程 × 10000 次 `count++`，期望 100000：

| 版本 | 实际值 | 耗时 | 是否正确 |
|---|---|---|---|
| `static int count` | **29370** | 4ms | ❌ 丢失约 71% 的更新 |
| `static volatile int count` | 略高于 29370，仍远小于 100000 | — | ❌ 仍然错 |
| `static synchronized void inc()` | **100000** | 23ms | ✅ |
| `AtomicInteger.incrementAndGet()` | **100000** | 9ms | ✅ |

### 关键结论

1. **`count++` 是三步**：读 → 加 → 写。两个线程可能都读到 50000、都算出 50001、都写回 → 只生效一次。
2. **`volatile` 让错误变少了一点，但没有让错误消失**——这是「可见性 ≠ 原子性」最直观的证据。它保证读到最新值，保证不了三步不被打断。
3. 程序不报错、不崩溃、退出码 0，**只是默默算错**。这种 bug 在真实系统里极难复现（依赖核心数与调度时序）。

### 为什么 AtomicInteger 比 synchronized 快（9ms vs 23ms）

| | `synchronized` | `AtomicInteger` |
|---|---|---|
| 策略 | 悲观锁：一次只放一个线程，其他挂起 | CAS 无锁：读值 → 试写 → 被改过就重试 |
| 竞争激烈 | 频繁挂起/唤醒，开销大 | 大量空转重试，可能反而变慢 |
| 竞争轻微 | 有固定开销 | 更快 |

**低竞争下 Atomic 更快，高竞争下不一定**——这是「无锁 vs 悲观锁」的取舍。

## 语法点：`synchronized` 的两种合法形态

```java
synchronized (锁对象) { ... }          // 形态 A：同步块，括号里必须是对象引用
static synchronized void inc() { ... } // 形态 B：同步方法
```

- `synchronized (count++)` **编译不过**——括号里要的是锁对象，不是表达式。
- 形态 B 是形态 A 的简写：实例方法锁 `this`，静态方法锁**当前类的 Class 对象**。
- 这里 `count` 是 `static`，所以必须是 `static synchronized`（锁 `AtomicityDemo.class`，全局唯一）；写成实例方法会导致「每个对象一把锁」，多实例之间不互斥，照样错。
- 生产代码更推荐显式同步块，锁的作用域更精确（只锁必要几行）。

## 面试口径（一句话版本）

> Java 线程有 6 种状态，`Thread.State` 描述的是「在等什么」：等锁是 `BLOCKED`，无期限等待是 `WAITING`，有期限等待（含 `sleep`）是 `TIMED_WAITING`。
>
> `volatile` 保证可见性和禁止重排序，不保证原子性；`synchronized` 和 `AtomicInteger` 保证原子性，后者基于 CAS 无锁实现，低竞争下更快。
